# EyeCare 자연 관측형 개발 계획 v0.2

2026-10-10 · 구현 전 계획 · 기준 APK 0.2.1-alpha

[현재 PRD](../../EyeCare_PASSIVE_PRD_2026-10-10.md) · [엔진](../../EyeCare_FATIGUE_DESIGN_2026-10-10.md) · [벤치마크](BENCHMARK_PROTOCOL.md) · [수치 계약](passive-spec-v0.2.json)

**폐기:** 매번 시선 표적 보정, 얼굴/거리 정렬, 100초 검사, 표준 화면을 보고 수동 PRE/POST 측정하는 개발 순서. 개발의 첫 확인은 다른 앱을 자연스럽게 사용하는 동안의 플랫폼 수명·관측률·자원이다.

## 1. 개발 순서

| 단계 | 우선순위 / 예상 시점 | 작업 | 산출물과 통과 조건 |
|---|---|---|---|
| G0 실행 가능성 | P0 / 1주 | 화면+camera FGS 동시 실행, 백그라운드 camera 해제/재획득, 경쟁·잠금·죽음, 전력 | 제조사 3종의 수명/재획득/60분 자원 보고. 허용 자동화와 재개 UX 고정 |
| G1 관측 기반 | P1 / 1~2주 | 수집/시각/상태 계약, 초기·중간·30분 일정, 조도, 예산, 기존 30분 종료 제거 설계 | 30분을 넘어 관측 가능한 세션, 시간 보존/부분 결과, 화면 회귀 없음 |

시점은 Android 1명과 CV/ML 1명, 파트타임 연구/QA 지원을 가정한 작업 추정이다. 한 명이 모두 수행하면 늘어난다. 참가자 모집과 기준 장비 준비는 G0부터 병행한다. 알파 4~6주, 파일럿/모델 선택 8~12주가 초기 가정이며 독립 평가 완료와 스토어 출시일은 그 이후 자료로 재산정한다.

## 2. G0 — 첫 주의 필수 확인

| ID | 작업 | 구현 후보 / 근거 | 완료 기준 |
|---|---|---|---|
| P0-01 | 화면+눈 관측 작은 기술 실험 | 기존 ProjectionService + 별도 camera FGS, 보이는 Activity에서 시작 | 다른 앱 사용 중 화면/눈 timestamp 동시 확보, 정렬 UX 없음 |
| P0-02 | 간헐 카메라 수명 | FGS를 살아 있게 둔 자원 해제/재획득과 계속 연결 비교 | OEM별 허용 여부, camera-open/NN duty, 배터리·경쟁 복귀 |
| P0-03 | 동의/중단 | 앱 공유/전체 공유, 잠금, 시스템 chip 중지, 권한/프라이버시 스위치 | 실제 중지·부분 결과·새 동의 진입. 옛 token 재사용 없음 |
| P0-04 | 실패·경쟁 | 카메라 앱/화상통화, 앱 강제 종료/프로세스 죽음, 회전 | 다른 앱 카메라 방해 최소화, 재시도 상한, 실제 관측 상태 |
| P0-05 | 자원과 심사 적합성 | 같은 콘텐츠 OFF/화면/화면+눈 60분, 실제 FGS 목적 검토 | PSS·전력·열·jank 결과, 해당 기능의 Play 신고/설명 계획 |

카메라 간헐 운용을 문서만으로 승인하지 않는다. CameraX는 Activity가 가려졌다고 자동 종료되는 일반 화면 lifecycle과 분리하고 서비스의 lifecycle/Camera2 경로를 평가한다. 적법하게 시작한 FGS를 종료한 뒤 background timer에서 새 camera FGS를 만드는 방식은 채택하지 않는다.

간헐 자원 재획득이 불안정하면 계속 연결 + 낮은 분석 duty를 비교한다. 이 경우 camera-open 절감 목표를 달성했다고 표시하지 않는다. 전력 예산을 넘으면 눈 특징/해상도/빈도·지원 기기를 조정한다. 자동 눈 관측을 만족하지 못하면 그 제약을 공개하고 다음 모델 단계 전에 설계를 수정한다. 사용자 정렬 검사로 되돌리지 않는다.

한 번 동의 후 잠금/재부팅까지 무인 재개가 가능한지에 대한 답은 일반 Android 앱에서는 보장 불가다. 승인된 세션 안의 자동화로 구현 범위를 고정하고 위젯/알림 재개를 설계한다. 더 강한 요구에는 OEM/시스템 권한 연구를 별도 과제로 둔다. [MediaProjection](https://developer.android.com/media/grow/media-projection), [FGS 제한](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start)

## 3. G1 — 기존 화면 엔진과 관측 계약

1. 기존 engineVersion·high-change 경계·유효 dt·어두운/보호 화면·제외 시간 지표를 유지한다.
2. captureEpochId와 wall/monotonic/camera timestamp 정렬·불확실성을 정의한다.
3. 10초 화면 창과 60초 센서 창, 실제 camera-open/eye-valid/pulse-valid/unknown-use를 분리한다.
4. 기본 0~3분 60초, 5·10·15·20·25분 45초, 27~30분 60초의 일정과 재시도/트리거 예산을 구현한다.
5. high-change 유효 시간 최근 60초 중 ≥20초이면 관측을 앞당기되 중복 이벤트를 병합한다. 화면 관측이 없으면 시각 트리거 불가.
6. 기존 SessionLimits.MAX_MS=30분과 MainActivity의 30분 진행률을 변경 대상으로 명시한다. 30분은 checkpoint로 바꾸고 공유 종료·사용자 중지·심한 발열 조건은 유지한다.
7. 기존 25분 알림과 새 30분 케어 알림이 중복되지 않도록 정책을 하나로 통합한다.
8. lux on-change/센서 age·가림, app category/confidence를 추가한다. 잠금 후 센서가 살아 있는 척하지 않는다.

30분 강제 종료 제거는 현재 문서 변경과 별개인 후속 코드 작업이다. 현재 APK 동작은 아직 25분 알림/30분 종료다. 장시간 실행 안정성·고정 버퍼·종료 flush를 확인한 후 변경 APK를 배포한다.

## 4. G2 — 자연 눈 관측 엔진

| ID | 작업 | 검증 |
|---|---|---|
| EYE-01 | 랜드마크와 눈 폭 정규화, 좌우/회전/카메라 좌표 | 동일 clip 재생·기기 회전·한쪽 눈, 영상/센서 시각 |
| EYE-02 | 검출 품질과 개방도 분리 | 눈 감김이 q 필터로 버려지지 않는 수동 라벨 비교 |
| EYE-03 | blink/long closure 상태 기계, gaps | 불완전 이벤트를 확정하지 않음, 실제 FPS별 precision/recall |
| EYE-04 | 자연 열린 눈 기준 prior/분위수 | 초기 눈 감김·작은 눈·안경·하방 시선, 비교 중 기준 고정 |
| EYE-05 | 눈/머리 방향 변동 proxy | 머리 움직임과 눈 움직임의 분리, 보정 없는 조건별 오류 |
| EYE-06 | 전후 창/특징 마스크 | 초기/종료 부족·자세 변화 시 Δ/null과 reason |

닫힌 눈 검출 문제·상하 시선에 따른 개방도 차이가 가장 먼저 해결할 오류다. 기존 NeuroLens 수학은 고정 커밋 자산과 동일 입력 비교로 이전하지만 보정 과제·활성화되지 않은 시선 잔차 모델은 자동 이식하지 않는다.

15fps 추론이 blink 지속시간을 손상하면 해당 특징을 보류하거나 30fps/가벼운 ROI 경로를 평가한다. 설정 FPS를 실측 FPS처럼 기록하지 않는다. 눈을 반쯤 감은 사용자에게 크게 뜨라는 안내를 띄우지 않는다.

## 5. G3 — 사용 가능한 관측 알파

- 메인 화면은 케어 시작/종료·실제 관측 상태·오늘 기록 중심으로 단순화.
- 시간 알림과 관측 사실 카드부터 제공. 학습 전 피로 점수는 null/그림자 상태.
- schema 3 저장·파일 공유·PC 전송·자동 집계를 추가하고 schema 1/2를 보존.
- 수집기는 모델/전처리 버전, 전후 성공/실패, 자세/조도, 품질별 출력률, 자원 요약을 보여줌.
- 카메라 미관측·개방 중 눈 없음·권한 종료·scheduled-off를 다른 이유로 표시.
- 최근 100개 UI/기존 30일 보존과 확장 기록의 용량·삭제 계약 확인.
- 실사용/test/research 자료의 식별과 중복/revision 규칙 유지.

알파의 완료 결과는 ‘사용자가 정렬하지 않고 30분 쓴 기록을 폰에서 내보내면 PC에서 합쳐볼 수 있음’이다. 해당 알파를 검증된 눈 피로 모델 출시로 부르지 않는다.

## 6. G4/G5 — 보정·보조 지표·학습

G4에서 30명 반복 자연 사용의 라벨 분포와 조건별 확보율을 먼저 본다. 라벨 범위가 좁거나 졸림과 피로를 구별하기 어렵다면 데이터 설계/목표를 수정한다. 프레임이 많다는 이유로 큰 모델을 학습하지 않는다.

보정은 참조로 확인한 pitch/노출/기기의 측정 오차부터 학습한다. 어두운 환경의 실제 부담까지 정규화로 지우지 않는다. 개인 기준선은 과거 자연 관측에서 인과적으로 만들고, 미래 방문에서 기여를 확인한다.

rPPG는 POS/CHROM·원래 RGB·화면 조명 동조 QC·접촉 HR 참조, 거리 특징은 카메라 내재 파라미터/참조 거리부터 평가한다. pulse 안정 신호가 안 나오면 피로 모델에서 빠질 수 있고 HRV는 별도다. 거리로 시력을 추정하는 작업은 만들지 않는다.

최종 피로 모델은 M0~M4의 기여·누락·경량 비용을 비교해 하나를 선택한다. current/Δ NRS·예측 구간·출력률을 평가하며 현재 연구 정답 응답은 입력에서 제외한다. 초기 NRS가 반드시 있어야 하는 모델은 무응답 제품 모델로 승격하지 않는다.

G5의 train/validation/locked test는 사람 단위 60/20/40명 초기 가정이다. 파일럿 사람은 새로운 locked test에 넣지 않는다. 특징/모델/보류/알림 임계값을 고정한 후 독립 시험을 보고, 실패하면 새로운 평가 자료로 다음 버전을 검증한다.

## 7. G6 — 알림·리포트·제품화

눈 반응 포함/화면 기반/근거 부족을 짧게 구별한다. 초기/종료 눈 자료가 부족하면 전후 눈 피로 측정 문구를 숨긴다. 피로 증가 알림은 검증된 변화·두 결과 유지·불확실성 조건으로, 시간 알림은 30분 사용 사실로 보낸다.

기본 휴식 알림 하루 4회·최소 30분 간격, 세션별 끄기를 둔다. 재개 상태 알림은 휴식 알림과 구별하고 상태 변화 한 번에만 알린다. 모든 lock/unlock마다 재개를 재촉하지 않는다. 알림 정책은 현장 오탐·해제·휴식 행동 자료로 검토한다.

스토어 문구는 지원되는 자동 관측 기간과 원본 미저장·기기 내 처리·재개 동의를 설명한다. 시력/질환 진단, 모든 환경의 정밀 시선, 한 번 동의로 영구 캡처를 광고하지 않는다. 점수 모델보다 ‘자동으로 놓치던 쉬는 순간을 알려주는 경험’을 첫 화면에서 전달한다.

## 8. 자원 최적화의 순서

1. 실제 전력 원인을 화면 projection / camera sensor / ISP / landmark / pulse / model / 저장으로 분해.
2. 카메라를 놓는 간헐 경로가 유효한지 확인. NN 실행 횟수 감소와 카메라 전력 절감을 구별.
3. 이벤트 병합·종료 창 예산 예약·고정 배열·최신 프레임 풀·수치 링 버퍼.
4. 해상도/15 vs 30fps·추론 delegate를 실제 기기에서 비교. ROI만의 최적화가 eye 오류를 늘리지 않는지 확인.
5. 저신뢰 pulse를 빠르게 중단하고 열 상승 시 보조 특징부터 줄임.
6. 실측에 맞춰 지원 기기/모드 확정. 메모리·배터리 목표가 달성되기 전 ‘상시 저전력’을 주장하지 않음.

측정 목표는 버퍼 ≤20MiB, 추가 PSS ≤80MiB/총 ≤180MiB, 대조 대비 추가 소모 중앙값 ≤5%p/시간이다. 최악 기기·분산·jank를 함께 보고한다.

| 눈 이벤트 오류 | 독립 수동/고속 부분 라벨 | 조건별 precision/recall·duration error |
| 조명 맥박 오수용 | 기준 HR·음성 대조·콘텐츠 조명 변화 | pulse 오차/출력률·제외 사유 |
| 모델 누출/과신 | 사람 분할·미래 방문·누락·새 기기·잠금 시험 | model card·오차/coverage·rollback |
| 자원 과다 | 60분 대조 반복, 장시간 고정 버퍼 | 전력·PSS·열·jank·개방률 |
| 알림 불편 | 전향 성인 사용자 관찰 | 유용성·오탐·꺼짐·재사용 |

센서/시간/보고서/모델의 실패를 재현하는 필수 검증부터 수행한다. 문서 변경만으로 APK 테스트 통과를 보고하지 않는다. 정상 사용자에게 검사 과제를 돌려 품질을 확보하는 방식은 완료 기준을 만족하지 않는다.

## 10. 다음 구현에서 할 일

첫 코드 작업은 P0-01~05다. 가능한 camera 수명과 자원 비용이 정해지면 G1의 시간 계약/스케줄러, G2의 눈 개방·blink 상태 기계 순서로 진행한다. 첫 30분 자연 사용 자료가 확보된 뒤 보정/피로 학습으로 들어간다.

전달물은 새 APK, 호환 보고서/수집기, 기기별 실행 범위, 자연 사용 bench 결과다. 검증된 피로 모델은 별도 승격 전달물이며 지금 계획 문서 작성 완료와 구별한다.
